# P32 설계 문서 — 창고동 실사형 재설계 (밴드형 다중 통로 + 렉 900기 안팎)

> 상태: **설계 초안 — 검토 필요.** `docs/p20~p31-*.md`와 같은 형식.
>
> 요청 원문: 현업에서 쓰는 창고동 스크린샷 첨부 + "창고동의 모양을 바꾸고 싶은거야...
> 이런 느낌으로 만들고 싶어." 확인된 요구사항:
> - `CP1`/`CP345` = 충전 포인트(P29 "충전 코너"와 같은 개념)
> - 밴드마다의 통로를 **전부 실제 AGV 경로**로(시각용 배경 아님, 완전히 사실적)
> - 렉 수량은 300이 아니라 **참고 이미지의 실측 밀도**(약 500~900+)에 맞춤
>
> **`docs/p31-warehouse-floor-expansion-design.md`를 대체한다.** 이 밀도면 단일 층으로
> 목표(500~900+)를 넘기 때문에, P31이 감수했던 "엘리베이터 카 1대 병목"(P27) 리스크
> 자체가 필요 없어진다. 층을 늘리는 대신 **1개 층의 구조를 재설계**하는 쪽으로 방향을
> 바꾼다.

## 0. 배경 — 지금 구조와 근본적으로 다른 지점

| | 현재(`NodeMap.java`) | 참고 이미지 |
|---|---|---|
| 통로 | 2개(상단 y=9, 하단 y=18) — WH·PROD·QC 세 건물을 관통하는 유일한 통로 | 밴드마다 1개 — **12개 안팎** |
| 구획 | 4개 discrete 베이(벽으로 분리) | 벽 없는 연속 그리드, 밴드 단위로 반복 |
| 렉 배치 | 베이당 2열×3행 = 6기, 4베이×24기/층 | 밴드당 2행 × 열 다수(30~40개대로 추정) |
| 렉 총량 | 72기(3층) | **500~900+**(1개 층 기준으로 추정) |
| 충전 포인트 | 없음(전력은 P27 배터리 로직으로만 존재, 물리적 충전소 노드는 미표현) | `CP1`, `CP345` — 좌하단 코너에 클러스터 |
| 통로 진입 방식 | 없음(2개뿐이라 진입 개념 자체가 단순) | 좌우 끝에서 각 밴드로 진입하는 구조로 보임(빗 모양) |

P20에서 라우터를 컴파일타임 규칙 기반에서 **노드-엣지 그래프 + A*/Dijkstra**로 이미
교체해뒀기 때문에, 통로가 2개든 12개든 **알고리즘은 안 바뀐다** — 이건 새 라우팅
로직이 아니라 **훨씬 큰 데이터셋**의 문제다. 다만 아래 D6에서 다루듯, 기존 렉코드
체계와 호환이 안 돼서 이번엔 "추가"가 아니라 "교체"가 된다는 점이 P28/P30과 질적으로
다르다.

## 1. 핵심 원칙 재확인 (P20~P30 계승 + 신규 1개)

| 원칙 | 이 설계가 지키는 방법 |
|---|---|
| 좌표는 코드와 분리 | `RackMap`은 코드 집합만 가짐(P21) — 재발번해도 이 분리 구조 자체는 안 건드림 |
| PROD/QC 쪽 계약 유지 | `WH-GATE-U`/`WH-GATE-L`은 좌표값만 조정하고 존재 자체·역할은 그대로(생산동은 안 건드림) |
| AMR/AGV 경계 유지(P22) | 창고동 내부는 여전히 AGV 전용, 새 스파인 통로도 AGV만 다님 |
| 배타적 자원 패턴 재사용(P27) | 좁은 밴드 통로의 교착 방지에 엘리베이터와 같은 패턴 적용(D3) — 새 동시성 모델 발명 안 함 |
| **[신규] 무변경 원칙의 예외를 명시한다** | 이번 작업은 D6에서 "추가"가 아니라 "교체"임을 인정하고, 그만큼 리스크·롤백 계획을 더 무겁게 잡는다(4절) |

## 2. 확정 결정 (D1 ~ D7)

### D1. 토폴로지 — "빗(comb)" 구조: 좌우 스파인 + 밴드별 가로 통로

```
WH-SPINE-L(좌측 세로 스파인)                    WH-SPINE-R(우측 세로 스파인, 게이트 방향)
   │                                                    │
   ├── 밴드1 통로 ──[렉행][렉행]──────────────────────── ┤
   ├── 밴드2 통로 ──[렉행][렉행]──────────────────────── ┤
   │        ...(밴드 12개)...                            │
   └── 밴드12 통로 ─[렉행][렉행]──────────────────────── ┘
```

- 우측 스파인이 기존 `WH-GATE-U`(y=9)·`WH-GATE-L`(y=18)과 만나는 지점을 유지해
  **PROD로 넘어가는 계약은 안 바뀐다** — 생산동 쪽 좌표·로직 무변경.
- 좌측 스파인은 참고 이미지의 바깥 점선 테두리 역할(도크→밴드 진입, 대칭 동선).
- 밴드 통로는 전부 실제 경로(요청대로) — 시각용 배경 통로는 없음.

### D2. 렉 그리드 — 예시안: 밴드 12개 × 2행 × 열 38개 = 912기

| 항목 | 값 | 비고 |
|---|---|---|
| 밴드 수 | 12 | 참고 이미지 밴드 수 추정치(10~11) + 여유 |
| 밴드당 행 | 2 | 이미지와 동일 |
| 행당 열 | 38 | 912 ÷ 24(밴드×행) ≈ 38 |
| **합계** | **912** | 요청 범위(500~900+) 상단 근접 |

정확한 숫자는 구현 단계에서 캔버스 크기(D7)를 실제로 잡아본 뒤 조정 — 이 표는
"이 정도 규모"라는 출발점이지 확정치가 아니다.

### D3. 밴드 통로 = 배타적 자원(one-lane) — 데드락 방지

밴드 통로가 좁고 길면(1차선에 가까운 구조), 두 AGV가 마주 볼 때 교착 위험이 커진다.
`docs/BACKLOG.md`에 이미 실제로 겪은 사례가 있다: "leg 예약 도입 중 겪은 hold-and-wait
교착." 통로가 2개에서 12개로 늘면 이 유형의 충돌 지점도 그만큼 늘어난다.

대응: 밴드 통로 하나를 P27의 엘리베이터와 같은 **배타적 점유 자원**으로 취급 — 한
번에 한 AGV만 그 밴드에 들어간다. 새 동시성 모델을 만들지 않고 `TrafficController`의
기존 구간 잠금 패턴을 밴드 단위로 재사용한다.

**주의**: 밴드 12개를 전부 배타적 단일 점유로 두면 동시에 최대 12대까지만 밴드
안에서 작업 가능 — 로봇 대수가 그보다 많아지면 밴드 진입 대기열이 생긴다(P27의
엘리베이터 큐와 같은 성격). 이번 설계에서 의도한 제약으로 남겨두고, 필요하면
후속에서 밴드별 대기열 길이를 Prometheus로 노출한다(P31 D3에서 다뤘던 것과 같은
관측 패턴).

### D4. 충전 포인트 — P29 패턴 재사용, 넘버링만 확장

P29(창고 충전 코너)가 이미 있는 개념이라 새로 설계하지 않는다. 좌하단 코너에
클러스터로 배치(참고 이미지와 동일 위치), 코드는 `CP1`, `CP2`... 순차 넘버링.

**확인 필요**: 참고 이미지에 `CP345`처럼 큰 번호가 보이는데, 이게 실제 충전 포인트가
345개 이상 있다는 뜻인지, 아니면 다른 넘버링 규칙(예: 위치 기반 ID)인지 불명확하다.
이번 설계는 **P29와 같은 소규모 클러스터**(4~8개 수준)로 가정하고 진행 — 대규모
충전소가 필요하면 별도 확인 후 D4를 다시 잡는다.

### D5. 층수 — 3층 → 1층으로 되돌린다 (P31 폐기)

밀도 자체로 목표(500~900+)를 넘기 때문에 층을 늘릴 이유가 없다. 기존 2층·3층은
이번 스코프에서 **그대로 둘지 아예 없앨지 결정 필요**(A: 2·3층 무변경 유지 — 지금처럼
1층과 좌표 겹치는 단순 구조로 남겨둠 / B: 2·3층 제거하고 1층 단일 건물로 단순화).
권장: **A** — 없애는 것 자체가 또 다른 마이그레이션이라 이번 스코프를 더 키운다.

### D6. 렉 코드 네이밍 — `WH-1F-B{밴드}-R{열}` (전면 재발번, 마이그레이션 필요)

기존 `WH-1F-R01~R24` 체계는 "4베이×6기" 구조를 전제로 한 코드라 밴드형 구조와
호환이 안 된다. **P28/P30처럼 새 코드를 추가하는 게 아니라, 기존 코드 자체를
폐기하고 전면 재발번한다.**

이게 이번 설계에서 가장 무거운 결정이다 — 기존 72개 로케이션·P26 안전재고 시드·
파렛트가 전부 새 코드로 마이그레이션돼야 한다. 4절(리스크)에서 구체적으로 다룬다.

### D7. 캔버스 크기 — `MAX_Y`(현재 26) 재산정 필요

12개 밴드 × (2행 + 통로 폭) 어림 계산만 해도 세로 방향이 지금 26보다 상당히
커진다. `layout_settings.height` 자체를 키워야 하는데, 이게 PROD/QC를 비롯한
다른 건물 좌표에 영향을 주지 않는지 확인이 먼저다(현재 모든 건물이 같은 캔버스
위에 나란히 배치되는 구조라, 캔버스가 커지면 상대 위치 재계산이 필요할 수 있다).

## 4. 리스크 & 롤백

- **D6(전면 재발번)이 이번 설계에서 가장 큰 리스크다.** P28/P30은 전부 "새 코드만
  추가"였고, 이번엔 기존 72개 렉코드가 통째로 없어진다. WMS의 로케이션·안전재고
  시드(P26)·파렛트가 코드 문자열로만 결합돼 있어서(P28 원칙: "WMS는 좌표를 전혀
  모른다"), 코드 자체가 바뀌면 그 결합이 깨진다 — **단순 좌표 이동이 아니라 데이터
  이관**이 필요하다.
- **롤백이 이전 P들보다 무겁다.** P28/P30은 새 마이그레이션 파일 하나로 롤백됐지만,
  이번엔 기존 데이터를 옮긴 뒤라 되돌리려면 이관 전 스냅샷을 복원하는 수준의 작업이
  된다. **구현 전에 반드시 별도 브랜치 + DB 스냅샷을 먼저 뜬다.**
- **밴드 통로 배타적 점유(D3)가 처리량을 제한한다.** 밴드 12개 = 동시 작업 가능한
  AGV도 사실상 12대 언저리로 제한됨 — 로봇 대수를 늘릴 계획이 있다면 이 상한을
  먼저 고려해야 한다.
- **캔버스 크기 변경(D7)이 다른 건물에 파급될 가능성.** 실측 전까지는 PROD/QC 좌표가
  안전한지 확신할 수 없다 — 실행 단계 첫 항목으로 이걸 먼저 검증한다.

## 5. 이번엔 안 하는 것

- **2층·3층에도 이 밴드 구조를 복제하는 것** — 밀도만으로 이미 목표를 넘기므로
  불필요한 확장. D5에서 2·3층은 기존 단순 구조로 그대로 둔다.
- **밴드 통로의 정밀 양방향 교통 신호(신호 체계)** — 이번엔 배타적 단일 점유(D3)로
  충분하다고 본다. 실측 후 병목이 심하면 후속으로 검토.
- **충전 포인트 대량 배치(수백 개)** — D4에서 확인이 안 된 채로는 P29 수준의
  소규모 클러스터로만 간다.
