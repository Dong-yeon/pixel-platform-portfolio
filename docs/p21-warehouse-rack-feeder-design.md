# P21 설계 문서 — 창고동 렉 취출 로봇(랙 피더) + WMS 물리 흐름 정합

> 상태: **설계 초안 — 착수 전, 승인 대기.** `docs/BACKLOG.md`의 관행("세부 설계를 먼저 문서로
> 확정하고 승인받은 뒤 착수한다")을 따른다. `docs/p20-layout-routing-design.md`와 같은 형식.
>
> 선행 문서: P11(레이아웃 서버화, factory가 평면도 소유) · P13(WMS 모듈) · P19(스텝 기반 주문
> 모델, 층간 엘리베이터 handoff) · P20(그래프 라우팅, `LaneGraph`/`TrafficController`).
> 이 문서는 그 위에서 "AMR과는 다른 종류의 로봇을 추가하려면 무엇을 건드려야 하는가"를 다룬다.

---

## 0. 요청 원문과 범위

> "창고동을 WMS로 좀 더 상세하게 하고 싶다. AMR이 있다고 생각하고, 4층 정도의 렉이 있고
> 그것을 빼서 AMR에게 주는 로봇이 따로 있다고 보고 진행한다 — **창고 안에서만 도는 로봇.**"

세 가지 요구를 코드 레벨로 옮긴다:

1. **AMR과 다른 로봇 종류**가 하나 더 있다 — 여기서는 **랙 피더(Rack Feeder)** 라 부른다.
2. 그 로봇은 **렉(4단 안팎)에서 실제로 물건을 꺼내 AMR에게 넘긴다** — 지금은 이 과정이
   존재하지 않는다(1절에서 근거).
3. 그 로봇은 **창고동 밖으로 나가지 않는다** — AMR의 레인망(`LaneGraph`)에는 올라가지 않는다.

---

## 1. 왜 지금 필요한가 — 코드로 확인한 현재의 구멍

**렉은 이미 있다. 하지만 아무도 렉에 가지 않는다.**

- factory `layout_racks`(V12)에 렉 27기가 실좌표·열·단·용량을 갖고 있다 — 1층 9기(4열×5단),
  2층 9기(3열×4단, **이미 사용자가 말한 "4층 정도"와 정확히 일치**), 3층 9기(2열×6단).
  대시보드 `RackShape`가 적재율로 색을 칠해 이미 그린다.
- WMS `locations`(V3~V5)가 렉 27기를 **로케이션**(재고를 갖는 단위)으로 갖는다 — 렉 코드가
  곧 로케이션 코드다(`WH-2F-R04` 등), `stocks` 테이블에 실제 수량이 있다.
- 그런데 **WMS V5 마이그레이션이 그 로케이션의 `node_code`를 렉의 실제 위치가 아니라
  그 층의 피킹존 노드(`WH-PICK`/`WH-2F-P1`/`WH-2F-P2`/`WH-3F-P1`/`WH-3F-P2`)로 덮어썼다.**
  주석이 이유를 스스로 밝힌다: *"층간 리프트는 모델링하지 않았고, AMR은 지상만 다닌다 —
  위층 물건은 리프트로 내려온 뒤 피킹존에서 실린다고 본다."*
- 그 결과 `OutboundOrder`가 fleet에 넘기는 `originNode`는 **렉이 아니라 이미 피킹존이다**
  (`OrderService.createOutbound` → `from.getNodeCode()`). AMR은 렉 근처에 간 적이 없다 —
  "이미 거기 물건이 있다"고 치는 것이다. 지도에 그려진 27개의 렉은 **적재율 색만 바뀌는
  배경 그림**이고, 어떤 로봇 이벤트와도 연결돼 있지 않다.

**이것이 진짜 문제다.** 렉을 더 예쁘게 그리는 게 아니라, "렉 → 피킹존" 구간을 지금 빠져
있는 물리적 이동으로 만드는 것 — 그리고 그 이동을 AMR이 아니라 **다른 로봇**이 맡는 것이
이번 작업의 핵심이다.

부수적으로 하나 더 발견했다: 위 V5 마이그레이션은 "렉이 어느 피킹존과 가까운가"(R01~R03은
위쪽 줄이라 P1, R04~R09는 아래 줄이라 P2)를 **WMS 쪽에 하드코딩**했다. 이건 좌표 문제라
factory/fleet 소관이지 재고 소관이 아니다 — 4절 D4에서 이 계층 위반도 함께 정리한다.

## 3. 목표 구조

```
                    ┌───────────────────────────┐
                    │  WMS OutboundOrder          │  origin = 렉 코드(예: WH-2F-R04) — 되돌린다(D9)
                    │  (재고 차감은 여전히          │
                    │   "운송 완료 통지" 시점)      │
                    └──────────────┬────────────────┘
                                   │ POST /api/tasks {originNode: "WH-2F-R04", destinationNode: "PROD-A1"}
                                   ▼
                    ┌───────────────────────────────────────────┐
                    │  fleet OrderService.create()                │
                    │  origin이 렉 코드다 → 두 주문으로 분할(D5)   │
                    └───────┬───────────────────────┬─────────────┘
                            │ 앞 레그                  │ 뒷 레그 (handoff_of로 연결)
                            ▼                         ▼
              ┌─────────────────────────┐   ┌─────────────────────────────┐
              │ 랙 피더 전용 주문           │   │ 기존 AMR 주문 (무변경)         │
              │ WH-2F-R04 → WH-2F-P1     │   │ WH-2F-P1 → PROD-A1(또는     │
              │ robotType=RACK_FEEDER    │   │ 층이 다르면 엘리베이터 체인)   │
              │ LaneGraph 미사용(D2)      │   │ robotType=AMR (기본값)       │
              └─────────────────────────┘   └─────────────────────────────┘
                     ▲ zoneCode로 배차 범위 제한(D1)     ▲ 기존 floor_no 배차 그대로
```

**핵심 전환**: "렉 → 피킹존" 구간이 AMR의 상상 속 이동에서, **랙 피더라는 별도 로봇 풀이
실제로 수행하는 주문 레그**로 바뀐다. 이미 있는 층간 handoff 메커니즘(`handoff_destination`/
`handoff_of`/`available_at`)을 "로봇 풀이 바뀌는 경계"로 일반화해서 재사용한다 — 새 상태
기계를 만들지 않는다.

## 4. 확정 결정 (D1 ~ D10)

### D1. 로봇을 종류로 나눈다 — `robots.robot_type` + `robots.zone_code`

```sql
alter table robots add column robot_type varchar(20) not null default 'AMR';
alter table robots add column zone_code varchar(30);  -- RACK_FEEDER만 사용, AMR은 null
```

- `robot_type` ∈ `AMR` | `RACK_FEEDER`. 기존 로봇 8대는 마이그레이션으로 전부 `AMR`(무변경).
- `zone_code`는 랙 피더가 담당하는 **피킹 클러스터**(피킹존 하나 + 그 존이 커버하는 렉들).
  AMR의 `floor_no`가 "이 로봇은 이 층을 못 벗어난다"였던 것과 같은 역할 — 랙 피더는 한 술 더
  떠서 **자기 존 밖의 렉에도 못 간다**(현실의 미니로드 AS/RS 셔틀이 자기 레인만 도는 것과 같다).
- `floor_no`는 그대로 유지(랙 피더도 층 개념은 있다 — 자기 존이 속한 층).

**왜 새 로봇 테이블을 안 만드는가.** `RACK_FEEDER`도 배차·상태·이벤트·MQTT 텔레메트리 파이프라인을
AMR과 **완전히 공유한다**(1절 구조도) — 다른 건 "어디까지 갈 수 있는가"뿐이다. 별도 테이블로
쪼개면 `RobotService`/`RobotLiveState`/이벤트 기록 코드가 전부 두 배로 갈라진다. 종류를 컬럼
하나로 두고 배차 필터에서만 구분하는 편이 기존 구조(floor_no로 AMR 풀을 나눈 전례, 2026-08-03)와
일관된다.

### D2. 랙 피더는 `LaneGraph`(AMR 공유 그래프)에 올라가지 않는다

렉을 `layout_nodes`/`layout_edges`에 정식 노드로 편입시키는 안을 검토했으나 기각한다.

- **P20-3에서 실제로 겪은 위험**: 그래프의 가상 진입점(anchor) 탐색이 "가장 가까운 연결로"를
  **x좌표만으로** 전역에서 고른다. 렉을 그래프 노드로 넣으면 AMR의 진입점 탐색이 렉 좌표를
  가까운 연결로로 잘못 고를 여지가 생긴다 — 지금 안정적으로 도는 `LaneGraph`/`TrafficController`
  (P20에서 검증에 가장 공들인 부분)를 건드리는 대가가 크다.
- **물리적으로도 맞다**: factory V12 주석이 이미 "렉은 커넥터에서 1.75 이상 떨어뜨린다(AMR
  주행과 겹치지 않게)"고 명시한다 — 렉 서비스 통로는 애초에 AMR 레인과 **분리된 공간**이라는
  전제가 이미 평면도에 있다. 그 전제를 그대로 살린다.

**대신**: 랙 피더의 이동은 **로컬 직선 이동**이다(존 안에서 현재 위치 → 목표 렉 정면 →
피킹존, 웨이포인트 2~3개). `TrafficController`의 구간 점유·`LaneGraph`의 다익스트라를 타지
않는다 — 한 존에 로봇 1대만 배치하면(D10)애초에 경쟁이 없어 교통정리가 필요 없다. 존당
로봇을 늘리는 건 8절(범위 밖)로 미룬다.

### D3. 렉 좌표는 새 캐시(`RackRegistry`)로 — 새 factory API는 필요 없다

`GET /api/layout`은 **이미** `racks: [{rackCode, buildingCode, floorNo, posX, posY, orientation,
columnsCount, levelsCount, capacityQty}, ...]`를 응답에 포함한다(대시보드가 이미 소비 중).
fleet의 `LocationRegistry`는 지금 이 필드를 **무시하고** 있을 뿐이다.

- `LocationRegistry`에 `racks` 맵을 추가로 파싱·캐싱한다(같은 5분 주기, 같은 폴백 원칙 —
  factory가 죽어도 랙 피더가 마지막으로 받은 좌표로 계속 동작해야 한다).
- 렉의 "정면 접근점"(피더가 서는 자리)은 `orientation`(V=세로/H=가로)에 따라 렉 중심에서
  고정 오프셋(예: 세로 렉이면 x±1.2)만큼 뗀 점으로 계산한다 — factory가 이미 "렉 반폭
  0.8 + 로봇 반경 0.95 ≈ 1.75" 간격 규칙을 문서화해 뒀으므로(V12 주석) 같은 값을 재사용한다.

### D4. 피킹존 매핑은 WMS가 아니라 fleet이 좌표로 계산한다 (계층 위반 교정)

1절에서 지적한 대로, "이 렉은 어느 피킹존이 가까운가"는 **물리적 사실**이지 재고 사실이
아니다. 지금 WMS V5가 렉마다 이 매핑을 손으로 박아 둔 것은 계층을 넘은 결정이다.

**결정**: fleet의 `RackRegistry`가 "이 렉의 층에 속한 피킹존 노드들 중 가장 가까운 것"을
직접 계산한다(엘리베이터의 `elevatorNode(floor)`가 "이 층엔 엘리베이터가 하나"라는 **관례**로
정한 것과 달리, 이건 여러 후보 중 **거리로** 고른다는 차이가 있다). WMS는 더 이상 "어느
피킹존"을 몰라도 된다 — D9에서 WMS 쪽 마이그레이션으로 되돌린다.

### D5. 주문 분할 로직을 "층 경계"에서 "로봇 풀 경계"로 일반화한다

지금 `OrderService.create()`는 `crossFloor`(스텝 간 층이 다른가) 하나만 보고 엘리베이터
handoff로 쪼갠다(`createSplitAtElevator`). 렉 취출을 또 하나의 특수 분기로 욱여넣으면
(`origin이 렉 코드인가?` 체크를 나란히 추가) 같은 모양의 분기가 두 개 생긴다.

**검토한 두 옵션**:

| | 옵션 A — 로봇 풀 경계로 일반화 (권장) | 옵션 B — 렉 케이스를 나란히 특수 처리 |
|---|---|---|
| 구현량 | 중간 — `crossFloor` 판정을 `requiredPool(step)` 비교로 교체 | 작음 — `createSplitAtElevator` 옆에 `createSplitAtRack` 하나 더 |
| 3번째 handoff 케이스가 생기면 | 조건 함수 하나만 추가 | 특수 분기가 세 개로 늘어난다 |
| P19 재정의 문서의 방향("엘리베이터 handoff가 스텝 모델로 녹는 방향")과의 정합 | 그대로 실행하는 것 | 반대 방향(특수 케이스를 하나 더 만듦) |
| 회귀 위험 | `crossFloor` 로직 자체를 건드림(기존 엘리베이터 handoff 재검증 필요) | 기존 엘리베이터 경로 무변경 — 회귀 위험 최소 |

**결정: 옵션 A.** 지금이 가장 싸게 일반화할 시점이다 — handoff 케이스가 정확히 2개일 때
공통 규칙을 뽑아내는 것과, 나중에 3번째가 생겼을 때(예: 출하장 도크→트럭 상차 로봇) 두 특수
분기를 보며 뒤늦게 일반화하는 것은 비용이 다르다. `docs/pixel-platform-roadmap.md` 0-A와
P19 재정의 커밋(`cc081cd`)이 이미 이 방향을 예고해 뒀다.

```java
// 스텝 각각이 요구하는 로봇 풀 — (floorNo, robotType, zoneCode) 튜플로 표현
record RobotPool(short floorNo, RobotType type, String zoneCode) {}

RobotPool requiredPool(String locationNode) {
    if (rackRegistry.isRackCode(locationNode)) {
        var rack = rackRegistry.get(locationNode);
        return new RobotPool(rack.floorNo(), RACK_FEEDER, rack.zoneCode());
    }
    return new RobotPool(locations.floorOf(locationNode), AMR, null);
}
```

`create()`는 지금의 "스텝 간 층이 섞이면(2스텝 한정) 엘리베이터에서 끊는다"를
"스텝 간 `requiredPool`이 바뀌면(2스텝 한정) **그 경계의 handoff 지점**에서 끊는다"로
바꾼다. handoff 지점은 경계 종류에 따라 다르게 정한다:

- 로봇 풀이 바뀌는 이유가 **층**이면 → 지금처럼 그 층의 엘리베이터 노드
- 로봇 풀이 바뀌는 이유가 **렉→AMR**이면 → D4가 계산한 그 렉의 피킹존 노드
- 스텝이 3개 이상인데 풀이 두 번 이상 바뀌면 → 예전처럼 명시적으로 거부(호출자가 스스로 끊게 함)

`handoff_destination`/`handoff_of`/`available_at` 필드는 **그대로 재사용**한다(의미를
"엘리베이터 승강 대기"에서 "다음 구간을 맡을 로봇 풀 대기"로 일반화할 뿐, 스키마 변경 없음).
`available_at`은 렉 취출의 경우 "픽업 완료 예정 시각"(현재 시각 + D7의 취출 소요시간)이 된다.

### D6. `FleetOrder`에 `robot_type` 추가, 배차 후보 필터를 두 정책 모두에 확장

```sql
alter table fleet_orders add column robot_type varchar(20) not null default 'AMR';
```

`OrderService.create()`가 분할 시 앞 레그(렉 주문)에 `RACK_FEEDER`, 뒷 레그(기존 로직)에는
`AMR`(기본값, 무변경)을 심는다. 배차 후보 필터는 **두 `AssignmentPolicy` 구현체 모두**
(`NearestBatteryAwareAssignmentPolicy`, `GraphCostAwareAssignmentPolicy`)에 같은 줄을
추가해야 한다 — floor 필터가 이미 양쪽에 중복돼 있는 것과 같은 자리에 넣는다:

```java
.filter(robot -> robot.robotType() == order.getRobotType())
.filter(robot -> order.getRobotType() != RACK_FEEDER || robot.zoneCode().equals(order.getZoneCode()))
```

`OrderService.dispatchOnce()`의 head-of-line 회피 로직(2026-08-03 수정분, "앞에서부터 훑어
배차 가능한 첫 주문")은 무변경으로 그대로 유효하다 — 자원 풀이 (층)에서 (층, 로봇종류, 존)으로
더 잘게 쪼개질 뿐, "맨 앞 하나만 보고 포기하면 다른 풀이 굶는다"는 같은 원리로 이미 방어돼 있다.

### D7. 취출 소요시간은 **불투명한 타이머**다 — 레벨별 애니메이션을 만들지 않는다

렉이 4~6단이어도, "몇 단에서 꺼내는지"를 시뮬레이터가 알 근거가 없다(WMS는 로케이션=렉
단위로만 재고를 갖고, 빈 단위 재고는 이번 범위 밖 — 8절). 없는 데이터로 "3단으로 팔을
뻗는" 애니메이션을 만들면 CLAUDE.md의 "없는 데이터를 시각 효과로 지어내지 않는다" 원칙을
정면으로 어긴다.

**결정**: 엘리베이터의 `elevatorTravelSeconds`(고정 12초, 이동 없이 대기만 표현)와 같은
패턴을 쓴다 — 랙 피더가 렉 정면에 도착하면 `rack.fetch-seconds`(기본 8초, 설정값) 동안
**멈춰서** 취출을 표현하고, 그동안은 위치 텔레메트리가 그대로(움직임 없음) 나간다. 지도에는
"이 렉이 지금 서비스 중"이라는 사실만 보여준다(실제 이벤트로 뒷받침됨 — 진행 중인 랙 피더
주문의 origin 렉이므로 지어낸 정보가 아니다).

### D8. MQTT 프로토콜은 **변경하지 않는다** — robot-sim에 랙 피더 타입만 추가

기존 `GOTO`/`started`/`step-done`/`failed` 어휘가 로봇 종류를 가리지 않는다 — 그대로 랙
피더에도 쓴다. robot-sim에 `RackFeederRobot`(또는 `VirtualRobot`에 종류 플래그, 구현 단계에서
결정)을 추가하고, D7의 정지 타이머만 AMR과 다르게 동작시킨다.

robot-sim은 fleet DB에 런타임 의존하지 않는 원칙(P11)을 유지해야 하므로, 랙 좌표의 **로컬
사본**이 필요하다 — 기존 `NodeMap`처럼, 그리고 기존 `NodeMapLayoutConsistencyTest`처럼
factory 마이그레이션과 대조해 어긋나면 빌드를 깨뜨리는 테스트를 **랙 좌표에도 추가**한다
(`RackMapLayoutConsistencyTest` 또는 기존 테스트 확장).

### D9. WMS: `Location.nodeCode`를 렉 코드 자체로 되돌린다 (V6 마이그레이션)

```sql
-- V6__rack_locations_own_node.sql (예시)
update locations set node_code = location_code
 where location_code ~ '^WH-[123]F-R\d+$';
```

`OrderService.createOutbound()`의 호출부는 **한 줄도 안 바뀐다** — 여전히
`fleetTaskClient.createTask(taskCode, from.getNodeCode(), request.toNodeCode(), priority)`
하나만 보낸다. fleet이 origin이 렉 코드임을 스스로 판별해 내부에서 두 구간으로 쪼갠다(D5) —
**WMS는 렉→피킹존 구간이 생겼다는 사실 자체를 모른다.** 이건 새로 만드는 경계가 아니라
엘리베이터 handoff에서 이미 검증된 것과 같은 경계다("WMS가 층 넘는 걸 몰라도 완료 통지 하나로
끝난다" — P19 코드 주석 그대로 재사용).

### D10. 랙 피더 배치 — 존 5개, 존당 1대로 시작

기존 렉 배치(2절 근거)를 피킹존 기준으로 묶으면:

| 존 | 층 | 담당 렉 | 대수(제안) |
|---|---|---|---|
| WH-PICK | 1F | R01~R09 (9기) | 2대 |
| WH-2F-P1 | 2F | R01~R03 (3기) | 1대 |
| WH-2F-P2 | 2F | R04~R09 (6기) | 1대 |
| WH-3F-P1 | 3F | R01~R03 (3기) | 1대 |
| WH-3F-P2 | 3F | R04~R09 (6기) | 1대 |

**⚠ 2026-08-04에 실제로 겪은 함정을 그대로 반복할 위험이 있다.** 그때 "존당 로봇 1대"로
위층 AMR을 배치했다가 그 1대가 충전에 들어가는 순간 존 전체가 멈췄다(자원 풀을 쪼갠 뒤
풀마다 여유를 안 본 사고). 렉 피더도 같은 구조(존당 1대)라 **같은 사각지대를 그대로
물려받는다.** 1차 배치는 위 표(6대, 존당 1~2대)로 가되, 데모 중 존별 유휴율을 관찰해
필요하면 여유가 0인 존부터 증차한다 — 이 항목은 "설계"가 아니라 "운영 관찰 후 조정"이므로
실행 단계에서 실측하고 조정한다(8절 범위 밖 목록의 "다중 랙 피더 교통정리"와 연결됨).

## 8. 이번엔 안 하는 것 (범위 밖 → 후속 항목)

- **빈(bin) 단위 재고 추적** — WMS는 여전히 렉 단위로만 수량을 갖는다. "몇 단에서 꺼냈는지"는
  추적하지 않는다(D7의 근거와 동일 — 없는 데이터를 만들지 않는다). 필요해지면 WMS에 별도
  bin 테이블을 추가하는 큰 작업이라 여기서 다루지 않는다.
- **존 안 다중 랙 피더 + 교통정리** — 존당 1대(또는 2대, D10)만 두고, 로봇끼리 부딪히는
  문제 자체를 배치로 피한다. 여러 대를 넣어야 한다면 존 내부에도 `TrafficController` 같은
  경량 점유 통제가 필요해지는데, 이번 범위는 "렉 → AMR 인계가 실제로 존재하게 만드는 것"에
  한정한다.
- **입고(inbound)도 랙 피더를 거치게 하기** — 지금 입고는 "운송 없는 데모 단순화"로 즉시
  재고 반영이다(WMS `createInbound` 주석). 출고와 대칭으로 만드는 건 별도 항목.
- **랙 피더 배터리/충전** — AMR과 같은 배터리 임계값 체계(20/25/30%)를 그대로 물려받을지,
  랙 피더는 도크 복귀 개념이 아예 필요 없을지(작업 반경이 좁아 상시 충전 스테이션 옆일 수도
  있다)는 실행 단계에서 정한다.
- **신규 건물/렉 확장 시 자동 편입** — P20-3가 "데이터만 추가하면 편입된다"를 AMR 그래프에
  대해 증명했다. 랙 피더 존도 같은 수준으로 만들지는 이번 범위 밖(존 매핑은 D4가 좌표로
  계산하므로 렉을 추가하면 자동으로 가장 가까운 존에 붙긴 한다 — 다만 "새 존 자체"를
  데이터만으로 만드는 것까지는 검증하지 않는다).
