## 통합 공장 지도 ✅ 1차 구현 완료 (대시보드 매핑 방식)

**통합 현황 탭에서 PixelFactory와 PixelFleet을 하나의 공장 평면도로 보여준다.**

지금은 두 모듈이 KPI 카드와 이벤트 타임라인으로만 합쳐져 있고, 지도는 PixelFleet
탭에만 있다. 같은 평면도 위에 설비와 AMR을 함께 그리면 "하나의 공장을 두 시스템이
관제한다"는 플랫폼의 요지가 한 화면에 드러난다.

- **설비** — 사각형, 상태별 색(RUNNING 초록 / IDLE 회색 / DOWN 빨강 / QUALITY_HOLD 주황)
- **AMR** — 원형, 실시간 이동 (지금 구현 그대로)
- **작업 흐름** — 진행 중인 운송 작업의 출발→도착을 선으로 연결하면 물류 흐름이 보인다

### 필요한 것

1. **설비에 좌표 부여** — 현재 `Equipment`에는 위치가 없다. 선택지:
   - (a) `equipments` 테이블에 `pos_x`, `pos_y` 컬럼 추가 (마이그레이션 필요)
   - (b) 대시보드/게이트웨이 쪽 레지스트리로만 매핑 (DB 변경 없음, 빠름)
2. **좌표계 통일** — fleet의 44×24 평면도를 플랫폼 표준으로 삼는다. 지금 노드 좌표가
   `control-service/LocationRegistry`, `robot-sim/NodeMap`, `dashboard/types.ts` 세 곳에
   중복돼 있는데(아래 항목), 통합 지도를 만들면 단일화 필요성이 더 커진다.
3. **설비와 노드의 관계 정의** — STATION-A가 곧 CNC-01이 있는 자리인지, 인접한 적재
   지점인지. 서사를 정하면 좌표 배치가 자연스러워진다.

> **(a) 정식화까지 완료 (P11).** `equipments.pos_x/pos_y` + `layout_nodes` + `layout_settings`.
> 설비를 늘리거나 옮겨도 대시보드를 고칠 필요가 없다(실측: DB에서 좌표만 바꿔 지도가 이동).

## 좌표 정의 단일화 ✅ 완료 (P11)

**pixel-factory가 평면도 마스터를 소유한다.** 평면도는 공장의 것이지 물류만의 것이 아니고,
설비·하역 지점·(P12의) POP 단말이 모두 같은 바닥 위에 있다.

| 소비처 | 방식 |
|---|---|
| 대시보드 | `GET /api/factory/layout` + 설비 좌표는 `Equipment`에 실려 온다. **하드코딩 좌표 0** |
| control-service `LocationRegistry` | 기동 시 + 5분 주기로 factory에서 받아 캐시. 실패 시 하드코딩 폴백 + WARN |
| robot-sim `NodeMap` | **그대로 둔다.** 시뮬레이터는 물리 세계를 흉내내는 쪽이라 서버가 알려주는 대로 위치를 바꾸면 안 되고, 서버가 죽어도 돌아야 한다. 대신 `NodeMapLayoutConsistencyTest`가 마이그레이션 SQL과 대조해 **어긋나면 빌드를 깨뜨린다**(좌표 하나를 틀리게 만들어 실제로 실패하는지 확인했다) |

### 남은 것 — `LaneGraph`의 통로 y·연결로 x

`traffic/LaneGraph`는 통로 y와 세로 연결로 x를 `static final`로 갖고 있고, 그 값으로 구간
이름(`AU:11-18` 등)까지 만든다. 동적으로 바꾸려면 교통 통제 전체를 건드려야 해서 P11 범위에
넣지 않았다. 대신 `LocationRegistry`가 서버 평면도를 받을 때 **통로 y가 다르면 ERROR 로그**를
남긴다 — 조용히 어긋나면 그린 선과 실제 주행이 갈리고 구간 점유가 엉킨다.

연결로 x는 아직 어디에도 마스터가 없다(레인망은 factory가 모르는 물류 개념이다).
fleet이 소유하는 게 맞을 수 있는데, 그러면 "평면도는 factory 것"과 경계가 미묘해진다 — 결정 필요.

### 서비스 간 인증(M2M)

`GET /api/layout`은 **인증 없이 열려 있다.** 평면도는 민감정보가 아니고(설비 위치·하역 좌표뿐),
fleet이 기동 시 읽어야 하는데 서비스 간 인증이 없어 토큰을 받을 방법이 없다. 그래서 fleet은
게이트웨이를 경유하지 않고 모듈에 직접 붙는다. M2M 인증이 생기면 이 엔드포인트를 닫고
서비스 토큰으로 게이트웨이를 경유하게 바꾼다.


## AMR 교통정리 ✅ 구현 완료 (전체 경로 예약 방식)

### "겹친다"는 세 가지 다른 문제였다

증상이 비슷해 보여 한 문제로 착각하기 쉬운데, 원인도 해법도 각각 다르다.

| 겹침 | 원인 | 해법 | 위치 |
|---|---|---|---|
| **정차 겹침** | 같은 노드를 고른 로봇들이 노드 좌표 그 점에 정확히 겹쳐 선다 | 로봇 인덱스로 노드 주변 반경 1.1에 원형 정차 자리 분배(결정적이라 재현 가능) | robot-sim `Simulator#spot` |
| **경로 겹침 / 가로지르기** | 두 점을 직선으로 이으면 대각선이 설비·스테이션을 관통한다. 실제 AMR은 그렇게 못 간다 | 레인망(가로 통로 2 + 세로 연결로 6)으로만 경로를 만든다. **대시보드도 같은 규칙으로 폴리라인을 그려** 화면과 실제 주행을 일치시킨다 | `traffic/LaneGraph`, dashboard `types.ts#routePoints` |
| **주행 중 충돌** | 두 대가 같은 구간에 동시 진입 | 구간 배타 점유 + leg 단위 예약 + 점진 반납 (아래) | `traffic/TrafficController` |

세 번째를 풀어도 첫 번째·두 번째는 남는다. 구간 점유는 **주행 중** 충돌만 막고,
정차 지점과 화면 표현은 통제하지 않기 때문이다.

**서버가 경로를 소유하고 구간 점유권을 관리한다.**

- 서버가 레인 그래프(`traffic/LaneGraph`)로 경로를 계산해 웨이포인트를 로봇에 지시한다.
  로봇은 스스로 길을 정하지 않는다 — 그래야 서버가 통제할 수 있다.
- `traffic/TrafficController`가 구간 점유를 관리한다. 지나갈 구간을 **전부 확보해야만**
  배차하고, 하나라도 막혀 있으면 작업은 PENDING으로 남아 다음 패스에서 재시도한다.
- 작업 완료·실패 시 점유를 해제한다.
- 점유 현황은 `GET /api/traffic/reservations`로 볼 수 있다.

### 고아 작업 복구 ✅

로봇이 지시를 놓치면(배포 중 구독 전 발행 등) 그 작업이 ASSIGNED로 굳어 **레인 구간을
영원히 점유**하고 함대 전체를 멈춘다 — 실제 배포에서 발생했다.
`StuckTaskWatchdog`이 배정 ACK 타임아웃(30초)과 주행 타임아웃(5분)을 감시해 실패 처리하고,
실패 경로가 점유 해제와 재큐잉을 수행한다.

### 구간별(leg) 예약 ✅ 구현 완료

배차 시 leg1(현재→픽업)만 예약하고, 로봇이 픽업 도착을 보고하면 그때 leg2(픽업→하역)를
예약해 두 번째 GOTO를 보낸다. 로봇이 한 번에 쥐는 구간이 절반으로 줄었다.

구현 중 실제로 터진 것 두 가지 — 둘 다 이 구조의 핵심이라 기록해 둔다.

1. **교착(deadlock)** — 처음엔 leg1을 쥔 채 leg2를 요청했다. 이게 hold-and-wait라
   로봇 4대가 서로가 쥔 구간을 기다리며 픽업에서 전부 멈췄다(완료 0건).
   → 픽업 도착 시 **leg1을 전부 놓은 뒤** leg2를 요청한다. 픽업 자리는 레인 밖이라
   놓아도 통행을 막지 않는다.
2. **leg2 오배달** — 작업은 배차 직후 IN_PROGRESS가 되므로, 상태만 보고 leg2를 보내면
   아직 leg1을 달리는 로봇에게 도착한다. 로봇은 "이미 작업 중"으로 거부하고 서버는
   보냈다고 여겨, 구간만 잡힌 채 아무도 안 움직였다.
   → 픽업 도착을 **실제로 보고한** 작업만 leg2 대상으로 삼는다.

검증: leg2 전달 9회, GOTO 거부 0회, 작업 지속 완료(처리량 약 2건/분).

### 남은 처리량 개선

실제 동시 이동은 여전히 1~2대다. 로봇 6대가 모두 작업을 배정받은 상태이므로 공급이 아니라
**레인 용량**이 한계다. 다음 지렛대는 **구간을 더 잘게 쪼개는 것** — 지금 가로 구간은
연결로 사이(7칸)가 통째로 하나여서, 같은 구간에 있는 한 뒤차가 못 들어온다.
연결로를 늘리거나 구간을 절반으로 나누면 로봇들이 줄지어 따라갈 수 있다.

- **충전 주행은 통제 밖** — 저배터리 복귀는 여전히 로봇이 스스로 결정한다.
  서버가 충전도 작업으로 만들어 배차하면 완전해진다.

### 🐛 배터리 20~24% 사각지대 — 함대가 영구히 멈췄다 ✅ 수정됨

P6 검증 중 발견. 세 값이 서로 안 맞아 로봇이 빠져나올 수 없는 구간이 생겼다.

| 값 | 위치 |
|---|---|
| 배차 최소 배터리 **25%** | `NearestBatteryAwareAssignmentPolicy.MIN_BATTERY_PERCENT` |
| 충전 시작 기준 **20%** ← 문제 | robot-sim `sim.low-battery-threshold` |
| 배터리는 **MOVING일 때만** 닳음 | robot-sim `Simulator.tickMoving` (`tickIdle`은 안 닳는다) |

작업을 20~24%에서 끝낸 로봇은 **배차받기엔 낮고, 충전 가려면 높고, 가만히 있으면
더 닳지도 않는다.** 그 상태로 영원히 IDLE이다. 로봇이 하나씩 이 구간에 빠지면서
결국 함대 전체가 멈췄다(실제로 6대 전부 20~23%에서 멈춰 있었다).

교통 교착과 증상이 똑같아 보이지만(전원 IDLE, 완료 0건) 원인이 전혀 다르다.
점유 현황(`GET /api/traffic/reservations`)이 **비어 있으면** 교통 문제가 아니라 이쪽이다.

**수정:** 충전 기준을 20 → **30**으로 올려 배차 기준(25)보다 높게 만들었다.
불변식 **"충전 복귀 기준 > 배차 최소 배터리"**를 양쪽 코드 주석에 박아 뒀다.

검증: 배터리가 30% 아래로 내려간 로봇이 사각지대에 머무르지 않고 충전으로 전환돼
복귀하는 것을 실측했다(AMR-03 → CHARGING → 96% → 작업 재개).

> **참고 — 0%로 돌아다니는 로봇은 멈춘 게 아니다.** 충전 판단은 `tickIdle`에서만 하므로
> 작업 수행 중에는 배터리와 무관하게 계속 간다. 작업이 끝나야 도크로 출발하고, 그 주행
> 중에도 계속 닳아 0%로 클램프될 수 있다. 도착하면 충전한다(실측: AMR-05 0% → 도크 도착 →
> 48%). 배차는 25% 미만 로봇에 새 작업을 주지 않으므로 결국 항상 충전으로 수렴한다.
> 현실성을 높이려면 저배터리 시 작업을 중단하고 복귀해야 하는데, 그건 "충전도 서버가
> 배차하는 작업으로" 만드는 아래 항목과 함께 풀 문제다.

근본 원인은 두 값이 **서로 다른 서비스**에 나뉘어 있다는 것이다. 아래 "충전 주행은 통제 밖"을
해결해 충전도 서버가 배차하는 작업으로 만들면 애초에 어긋날 수가 없어진다.

## 게이트웨이 중앙 인증 ✅ 구현 완료 (P6)

**발급은 모듈이, 검증은 게이트웨이가.** 게이트웨이는 사용자 저장소가 없어 토큰을 발급할 수
없으므로 로그인은 신원 담당 모듈(`AUTH_MODULE_URI`, 현재 pixel-factory)에 위임하고,
이후 모든 요청은 `AuthenticationGlobalFilter`가 관문에서 검증한다.

- 세 서비스가 **같은 `PLATFORM_JWT_SECRET`**을 쓴다 → 로그인 한 번, 토큰 하나로 전부 통한다.
  (이전에는 모듈마다 키가 달라 대시보드가 모듈마다 로그인하고 토큰을 2개 들고 있었다.)
- 통과한 요청에 `X-Auth-User`/`X-Auth-Role`을 붙이고, **클라이언트가 보낸 `X-Auth-*`는 항상 지운다.**
  이걸 빠뜨리면 헤더만 붙여 관리자로 행세할 수 있다 — 헤더 기반 신원 전달의 대표적 구멍이다.
- 모듈도 자체 JWT 필터를 유지한다(방어 심층). 9001/9002에 직접 붙어도 인증이 필요하다.

게이트웨이는 `shared`(공통 코어)를 의존할 수 없다 — `spring-boot-starter-web`(서블릿)을
api로 노출해서 WebFlux 게이트웨이가 서블릿 스택으로 떠 버린다. 그래서 검증에 필요한 만큼만
jjwt를 직접 가져왔다.

### 남은 것

- **`/ws/**`는 여전히 인증 없이 통과한다.** SockJS 핸드셰이크에 Authorization 헤더를 실을 수
  없어서다. 토큰을 STOMP CONNECT 프레임에 담아 검증하면 막을 수 있다.
- **권한(Role) 기반 접근 제어는 모듈 몫.** 게이트웨이는 "인증됐는가"만 본다.
- **사용자 저장소가 모듈마다 따로 있다**(`users` 테이블 2벌). 전용 인증 서비스로 분리하면
  `AUTH_MODULE_URI`만 그쪽으로 돌리면 된다 — 지금 구조가 그 갈아끼움을 전제로 짜여 있다.
- **리프레시 토큰 없음.** 2시간 만료 시 다시 로그인해야 한다.

**기사 자체를 플랫폼에 넣지 않는다.** 뉴스는 근거이고, 여기 적힌 것만 구현 대상이다.

### P16. 인증 경계 정리 (보안 하드닝)

> P15 배포 단계에 몰아둔 보안 항목을 앞당긴다. **근거가 생겼다** — IBM '2026 데이터 유출
> 비용 보고서'에서 침해 원인 공동 1위가 **API·애플리케이션·플러그인 보안 취약점(27%)**과
> **AI 워크로드 관련 클라우드 설정 오류(27%)**다. 우리가 열어둔 구멍이 정확히 그 두 종류다.
> 포트폴리오 관점에서도 "배포 직전에 급히 잠갔다"보다 "설계 단계에서 인증 경계를 정의했다"가 낫다.

작업

1. **`/ws/**` 인증** — SockJS 핸드셰이크에 Authorization 헤더를 실을 수 없으므로 토큰을
   **STOMP CONNECT 프레임**에 담아 검증한다. `ChannelInterceptor`에서 CONNECT 프레임의
   `Authorization` 네이티브 헤더를 읽어 검증하고, 실패 시 연결을 끊는다.
   - 게이트웨이가 아니라 **모듈(factory·fleet) 쪽**에서 막는다. 게이트웨이는 WS 업그레이드를
     프록시만 하고 프레임을 해석하지 않는다.
2. **M2M(서비스 간) 인증** — `GET /api/factory/layout`이 무인증으로 열려 있는 이유가
   "fleet이 기동 시 읽어야 하는데 토큰 받을 방법이 없어서"다. 서비스 계정 토큰을 도입하고
   이 엔드포인트를 닫는다. 그러면 fleet이 모듈에 직접 붙지 않고 **게이트웨이를 경유**하게 된다.
   - 가장 단순한 형태: 서비스별 고정 클레임(`sub=svc-fleet`, `role=SERVICE`)을 가진 장기 토큰을
     `PLATFORM_JWT_SECRET`으로 서명해 환경변수로 주입. 사용자 토큰과 role로 구분한다.
3. **설정 오류 제거** — `mosquitto.conf`의 `allow_anonymous true` → 계정 인증,
   게이트웨이 CORS `allowedOriginPatterns: "*"` → 실제 오리진 목록. (P15에서 P16으로 이동)
4. **인증 경계 문서화** — `docs/auth-boundaries.md`: 어느 경로가 누구에게 열려 있고
   왜 그런지. 표 하나면 된다. 열어둔 것을 **의식적으로 열었다**는 기록이 방어의 절반이다.

완료 기준

- [ ] 토큰 없이 `/ws/factory` STOMP CONNECT 시 연결이 거부된다
- [ ] `GET /api/factory/layout`에 토큰 없이 접근하면 401이다
- [ ] fleet이 서비스 토큰으로 게이트웨이를 경유해 평면도를 받아온다 (직접 접속 제거)
- [ ] 익명 MQTT 접속이 거부된다
- [ ] 허용되지 않은 오리진의 브라우저 요청이 CORS에서 막힌다

주의

- **M2M 도입 시 fleet 기동 순서에 의존이 생긴다.** 게이트웨이가 아직 안 떠 있으면 평면도를
  못 받는다 — 기존 폴백(하드코딩 + WARN)이 그대로 살아 있어야 한다. 폴백을 지우지 말 것.
- **STOMP 인증을 켜면 대시보드가 먼저 깨진다.** 대시보드가 CONNECT에 토큰을 싣도록
  같은 커밋에서 고친다. 서버만 먼저 잠그면 화면이 통째로 죽는다.

### P17. MCP 서버 (`platform/mcp-server`, :9005)

> **AI 에이전트가 이 공장을 조회할 수 있게 만든다.** 2026-07-30 착수한 과기정통부·IITP
> '실세계 능동행동형 에이전틱 AI 기술개발'(26개 산학연·180억) 세부 과제에 **MCP 표준 기반
> 멀티에이전트 협업**과 **기업 ERP를 스스로 이해하는 업무 동료**가 들어갔다.
> 컴포저블 아키텍처의 자연스러운 다음 소비자가 사람이 아니라 에이전트라는 뜻이다.

작업

1. `platform/mcp-server/` — 게이트웨이(9000) 뒤가 아니라 **옆에 서는 별도 프로세스**.
   게이트웨이의 공개 REST를 MCP 도구로 감싼다. 모듈 DB에 직접 붙지 않는다(원칙 2).
2. 초기 도구는 **읽기 전용 4개**로 좁게 시작한다.

   | 도구 | 내부 호출 |
   |---|---|
   | `get_equipment_status` | `GET /api/factory/equipments` |
   | `get_oee` | `GET /api/factory/oee?equipmentId=&from=&to=` |
   | `get_fleet_state` | `GET /api/fleet/robots` |
   | `find_events` | `GET /api/factory/events?type=&from=&to=` |

3. **인증** — MCP 서버가 서비스 토큰(P16)으로 게이트웨이를 경유한다. P16 선행 필수.
4. 쓰기 도구(작업지시 착수, 운송 작업 생성)는 **1차 범위 밖.** 읽기가 안정된 뒤 별도 승인.

완료 기준

- [ ] MCP 클라이언트에서 도구 4개가 보이고 실제 데이터가 반환된다
- [ ] "CNC-01 오늘 OEE 얼마야?" 같은 질의가 도구 호출로 해소된다
- [ ] MCP 서버를 내려도 대시보드·모듈은 정상 동작한다 (컴포저블 검증)
- [ ] 토큰 없이 뜬 MCP 서버는 도구 호출 시 401을 그대로 노출한다 (조용히 실패 금지)

주의

- **쓰기 도구를 성급히 열지 않는다.** 에이전트가 작업지시를 착수시킬 수 있게 되는 순간
  "저장 연타 = TOCTOU" 문제가 사람보다 빠른 속도로 재현된다. 3층 방어가 먼저다.
- **언어 = Python(FastMCP)로 결정.** 도구 스펙이 얇아 가장 빠르고, Python 학습 목적에도 맞다.
  Java 통일(플랫폼 스택 일관성)은 검토했으나 이 조각에는 과하다고 봤다.
  → 플랫폼의 Gradle 빌드 흐름 밖에 있으므로 `platform/mcp-server/`는 **자체 의존성 관리
  (`pyproject.toml` 또는 `requirements.txt`)**를 갖고, `scripts/`에 기동 스크립트를 따로 둔다.

### P18. 추적 그래프 — LOT/파렛트 4단 트리 (온톨로지 방향)

> 이미 `docs/pixel-platform-roadmap.md` 0-A에 "스캔 한 번으로 전 계층을 잇는 화면이 이
> 도메인의 하이라이트"라고 적어둔 것과 **같은 항목**이다. 여기서는 방향의 근거만 덧붙인다.
>
> 전자신문 ET단상(위즈코어 박승훈 대표) — 제조 AX의 병목은 모델 성능이 아니라
> **설계 데이터와 제조 데이터가 다른 언어로 존재해 연결되지 않는 것**이고, 그걸 잇는
> 게 온톨로지다. 조선일보 피지컬 AI 투자 기사 — **"데이터 순환 고리를 움켜쥔 회사에
> 프리미엄이 집중"**. 두 기사가 같은 말을 한다.

선행: P13(WMS·품목 마스터) + P14(QMS·부적합)가 있어야 이을 것이 생긴다. **P16·P17보다 뒤.**

방향만 기록

- 작업지시번호 / LOT / 작업LOT / 생산LOT / 자재박스바코드 / **파렛트번호** 중
  아무거나 입력 → 우선순위 `UNION ALL`로 해소 → 4단 트리
- 여기까지는 관계형으로 충분하다. **그래프 DB를 성급히 도입하지 않는다.**
  트리 깊이가 고정(4단)이고 순환이 없으면 재귀 CTE로 끝난다.
- 그래프가 필요해지는 지점은 "불량 → 원인 공정 → 자재 → 설계 특성"처럼
  **경로가 가변이고 역방향 탐색이 주가 될 때**다. 그때 판단한다.

### P19. Fleet API를 M4 모양으로 — 현장 규격을 기본기로 삼는다

> [CUSTOMER] 현장은 WMS가 **M4**(상용 AMR 군집관제 서버)를 거쳐 실물 로봇을 부린다.
> 근거 문서: `D:\happyeon\05.[CUSTOMER]\Book\M4 Fleet API.pdf` (HTTP + WebSocket, 176쪽).
>
> **목적은 호환 레이어가 아니다.** 남의 클라이언트를 받으려고 M4를 흉내내는 게 아니라,
> 현장에서 검증된 API 모양새를 **pixel-fleet 자체 API의 기본형**으로 삼는다.
> 실물 관제 서버가 왜 그 개념들을 갖는지(스텝, 봉인, 씬, 요청-응답 봉투)를
> 내 손으로 구현하면서 체득하는 것이 목표다. 그 결과로 자연히 M4를 쓰는 현장
> 통합 코드와도 대화가 통하게 되면 덤이다.

M4에서 가져올 뼈대 (fleet API를 이 모양으로 개편)

- **주문 = 다단 스텝.** `orders/create`가 steps 리스트(location + 동작)를 받고,
  미봉인 주문에 `add/update/delete-steps`, `stepFixed`(봉인) 개념까지.
  transport_tasks의 출발→도착 단일 이송을 스텝 리스트로 일반화한다 — 내부적으로
  이미 2구간(픽업+하역, 엘리베이터 인수인계)을 쓰고 있어 토대는 있다.
  **이게 P19의 몸통이다.** 지금의 handoff 특수 처리가 "스텝 2개짜리 주문"으로 녹는다.
- **주문 생애주기 동사를 넓힌다**: cancel(-batch)/suspend/unsuspend/
  complete-order(수동 완결)/retry-failed. 지금은 재시도만 자동이고 운영 개입 동사가 없다.
- **externalId 관례**: 상류(WMS)가 자기 번호를 실어 보내고 완료 통지에서 그걸로 되찾는
  구조 — 이미 taskCode로 하고 있으니 이름과 자리만 규격에 맞춘다.
- **WS 요청-응답 봉투**: `id/action/content` → `action::Reply` + `replyToId`.
  지금의 단방향 push(STOMP broadcast)에 "질의"가 없다 — 위치만 골라 묻는
  `RobotsPositionOnly::Query` 같은 걸 이 봉투로 연다.
- **로봇 운영 동사**: off-duty(배차 제외)/disabled/clear-alarm — 지금은 로봇을
  운영에서 뺄 방법이 시뮬레이터를 끄는 것뿐이다.

주의

- **176쪽 전량을 좇지 않는다.** DI/DO, soft-EMC, rbk-request, 지도 리소스 잠금 등
  하드웨어 제어 계열은 robot-sim에 대응물이 없다 — 개념만 문서로 남기고 뺀다.
- scene은 당장 1개(우리 공장)다. 다중 scene 구조를 미리 파지 말고,
  API 시그니처에 sceneId 자리만 잡아 둔다.
- 스텝 일반화는 fleet 도메인 개편이라 **마이그레이션·배차·교통통제가 다 닿는다.**
  착수 전에 계획을 먼저 세우고 승인 받는다(작업 규칙).
